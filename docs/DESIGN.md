# Azul Online — Проектный документ (DESIGN)

> Статус: **pending approval** (черновик плана, до утверждения не реализуем)
> Стек: TypeScript full-stack · WebSocket · Гостевой вход · In-memory(+Redis опц.) · 2–4 игрока · Классический Azul · Таймер с авто-ходом · Реконнект по токену · Docker · PWA · Стиль Azulejo
> Ревью: архитектурное ревью пройдено; учтены P0 (точный алгоритм подсчёта, sequencing ходов, скрытие мешка `toPlayerView`), P1 (порядок конца игры, частичный рефилл фабрик, lifecycle-события, инъектируемые часы), P2 (детерминизм `autoMove`, `ping`/`pong`).

---

## 1. Цели и принципы

**Цель:** Полностью онлайн мультиплеер Azul для телефона. Полный цикл: лобби с активными комнатами → создание → запуск → ходы в реальном времени с таймерами → подсчёт очков → конец игры → результаты.

**Принципы проектирования:**
1. **Чистое ядро (engine) без I/O.** Вся логика Azul — набор чистых функций `(state, action) → state`. Никаких сокетов, таймеров, БД внутри. Это делает TDD простым и быстрым.
2. **Сервер — авторитет.** Клиент никогда не считает очки и не валидирует ходы как истину. Сервер хранит состояние, применяет ходы, рассылает обновления. Клиент — отрисовка + отправка намерений.
3. **Тонкий транспорт.** WebSocket переносит события; вся бизнес-логика — в engine. Транспорт можно заменить, не трогая правила.
4. **Лёгкий старт.** In-memory хранилище за интерфейсом репозитория. Redis/Postgres подключаются позже без переписывания логики.
5. **Детерминизм для тестов.** Источник случайности (перемешивание мешка) инъектируется (seedable RNG), чтобы тесты были воспроизводимы.

## 2. Полные правила Azul (что реализуем)

**Компоненты:**
- 100 плиток: 5 цветов × 20 шт. Цвета: `blue`, `yellow`, `red`, `black`, `white` (внутренние коды; в UI — изразцовые текстуры).
- Фабрики (factory displays): **2 игрока → 5, 3 → 7, 4 → 9** фабрик. На каждую в начале раунда кладётся 4 плитки.
- Центр стола. В начале раунда пуст, кроме **жетона «1 игрок»** (first-player marker).
- Мешок (bag) и сброс (discard/lid). При нехватке плиток в мешке во время рефилла — пересыпаем сброс в мешок и перемешиваем. **Краевой случай:** если при заполнении фабрик опустели И мешок, И сброс — оставшиеся фабрики заполняются **частично** (или остаются пустыми). Это валидное состояние раунда (контракт теста A7).

**Планшет игрока:**
- **Pattern lines** (узорные ряды): 5 рядов вместимостью 1,2,3,4,5.
- **Wall** (стена/мозаика): сетка 5×5 с фиксированным шаблоном цветов (каждый цвет встречается в каждой строке и столбце ровно один раз — стандартная диагональная раскладка).
- **Floor line** (пол/штраф): 7 ячеек со штрафами `-1,-1,-2,-2,-2,-3,-3`.
- **Score track**: счёт игрока (старт 0, не опускается ниже 0).

**Фаза 1 — Offer (выкладка / выбор плиток), по очереди:**
Ход игрока = выбрать **один цвет** из **одной** фабрики ИЛИ из центра:
- Из фабрики: забираешь ВСЕ плитки выбранного цвета; **остальные плитки этой фабрики уходят в центр**; фабрика пустеет.
- Из центра: забираешь все плитки выбранного цвета. Если ты **первый**, кто берёт из центра в этом раунде — забираешь жетон «1 игрок» (кладётся на твой floor line, даёт штраф, но право первого хода в следующем раунде).
- Взятые плитки кладёшь в **один** узорный ряд:
  - Ряд должен быть пуст или уже содержать тот же цвет.
  - Нельзя класть цвет в ряд, если в стене этой строки этот цвет уже выложен.
  - Лишние плитки (сверх вместимости ряда) идут на floor line.
  - Можно (по желанию или вынужденно) положить часть/всё прямо на floor line.
- Фаза заканчивается, когда **все фабрики и центр пусты**.

**Фаза 2 — Wall-tiling (укладка стены + подсчёт), для каждого игрока:**
- Для каждого **полностью заполненного** узорного ряда: одну плитку перемещаем в соответствующую (по цвету) ячейку стены в той же строке; остальные плитки ряда идут в сброс.
- **Алгоритм начисления за уложенную плитку (точная спецификация — контракт теста A6):**
  ```
  h = длина непрерывного ГОРИЗОНТАЛЬНОГО ряда, в который попала плитка (включая её)
  v = длина непрерывного ВЕРТИКАЛЬНОГО столбца, в который попала плитка (включая её)
  если h == 1 И v == 1:  очки += 1           // одиночная плитка без соседей
  иначе:                 очки += (h>1 ? h : 0) + (v>1 ? v : 0)
  ```
  То есть плитку НИКОГДА не считаем дважды: ось длиной 1 (нет соседей по ней) не даёт очков, кроме случая полного одиночества (тогда ровно 1).
- Незаполненные узорные ряды остаются как есть на следующий раунд.
- **Floor line:** суммируем штрафы занятых ячеек (жетон «1» тоже занимает ячейку и штрафует по её позиции), вычитаем из счёта (не ниже 0). Floor очищается. Жетон «1 игрок» возвращается в центр и задаёт `firstPlayerIndex` — взявший его ходит первым в новом раунде.

**Конец игры — строгий порядок операций в `resolveTiling`/финализации:**
1. Уложить все полные ряды в стену и начислить очки по алгоритму выше.
2. Применить штрафы floor line (даже в финальном раунде — счёт может уйти к 0, но не ниже).
3. Проверить конец игры: завершена ли у кого-то **полная горизонтальная строка** стены (5 плиток).
4. Если да — игра заканчивается **после этого раунда**; начислить финальные бонусы и определить победителя.
- **Финальные бонусы:** +2 за каждую полную горизонтальную строку, +7 за каждый полный вертикальный столбец, +10 за каждый цвет, выложенный все 5 раз.
- Победитель — макс. счёт **после бонусов**. Тай-брейк: больше завершённых горизонтальных строк; если всё ещё ничья — общая победа (`winnerIds` — массив).

**Терминология запроса → реализация:**
- «Рынок» = фабрики + центр стола (источник плиток на ход).
- «Витрина» = планшет игрока: стена/мозаика (выложенные плитки) + табло очков.

## 3. Архитектура (монорепо)

```
azul/
├─ packages/
│  ├─ engine/        # @azul/engine — чистая логика Azul (ядро TDD)
│  ├─ shared/        # @azul/shared — общие типы, схемы WS-протокола (zod), константы
│  ├─ server/        # @azul/server — Fastify + ws, комнаты, сессии, таймеры
│  └─ web/           # @azul/web — React + Vite + PWA (фронтенд)
├─ docker-compose.yml
├─ package.json      # npm workspaces, общие скрипты
└─ docs/DESIGN.md
```

- **npm workspaces** (без лишних инструментов). Общие типы в `shared` импортируются и сервером, и вебом → один источник правды для протокола.
- `engine` не зависит ни от чего рантаймового (ни Fastify, ни ws). Только TypeScript + чистые функции.

**Технологии:**
- Backend: **Fastify** (HTTP для health/REST-лобби) + **ws** (нативный WebSocket; легче socket.io, нам не нужны фолбэки).
- Валидация сообщений: **zod**-схемы в `shared` (рантайм-проверка входящих WS-сообщений).
- Тесты: **Vitest** (engine + server). Один раннер на весь монорепо.
- Frontend: **React 18 + Vite + TypeScript**, **Tailwind** (тема Azulejo), **Zustand** (состояние), **Framer Motion** (анимации плиток), **vite-plugin-pwa** (manifest + service worker).

## 4. Доменная модель (типы в `@azul/shared`)

```ts
type Color = 'blue' | 'yellow' | 'red' | 'black' | 'white';
type PlayerId = string;          // стабильный id игрока в игре
const FLOOR_PENALTIES = [-1,-1,-2,-2,-2,-3,-3];

interface PlayerBoard {
  patternLines: (Color | null)[][];   // 5 рядов; длины 1..5; null = пусто
  wall: (Color | null)[][];           // 5x5; null = не выложено
  floor: (Color | 'FIRST')[];         // плитки/жетон на полу
  score: number;
}

interface GameState {
  players: { id: PlayerId; name: string; board: PlayerBoard }[];
  factories: Color[][];               // длина = 5/7/9
  center: Color[];
  centerHasFirstToken: boolean;
  bag: Color[];
  discard: Color[];
  currentPlayerIndex: number;
  firstPlayerIndex: number;           // кто начинает следующий раунд
  phase: 'offer' | 'tiling' | 'finished';
  round: number;
  winnerIds: PlayerId[] | null;       // заполняется в finished
  rngSeed: number;                    // для детерминизма/реплеев
  turnSeq: number;                    // монотонный счётчик ходов; +1 на каждый applyMove
}

// Ход игрока (intent)
interface Move {
  source: { type: 'factory'; index: number } | { type: 'center' };
  color: Color;
  target: { type: 'patternLine'; row: number } | { type: 'floor' };
}

// Публичный вид для рассылки (скрытая информация редактирована).
// bag НЕ раскрываем по составу (это даёт читерское знание вероятностей).
interface PlayerView {
  players: { id: PlayerId; name: string; board: PlayerBoard; connected: boolean }[];
  factories: Color[][];
  center: Color[];
  centerHasFirstToken: boolean;
  bagCount: number;            // только количество, не состав
  discard: Color[];            // сброс публичен в Azul
  currentPlayerId: PlayerId;
  firstPlayerId: PlayerId;
  phase: 'offer' | 'tiling' | 'finished';
  round: number;
  turnSeq: number;             // монотонный номер хода (для идемпотентности)
  you: PlayerId;               // получатель этого вида
  winnerIds: PlayerId[] | null;
}
```

Стандартный шаблон стены (строки):
```
B Y R K W
W B Y R K
K W B Y R
R K W B Y
Y R K W B
```

## 5. Game Engine — публичный API (ядро TDD)

Чистые функции, никаких побочных эффектов. Случайность — через инъекцию seed/RNG.

```ts
createGame(playerInfos: {id,name}[], seed: number): GameState
legalMoves(state): Move[]                       // все допустимые ходы текущего игрока
isLegalMove(state, move): boolean
applyMove(state, move): GameState               // бросает при нелегальном ходе
isOfferPhaseOver(state): boolean
resolveTiling(state): GameState                 // фаза 2: укладка + подсчёт + штрафы
startNextRound(state): GameState                // рефилл фабрик (с пересыпкой сброса)
isGameOver(state): boolean
finalizeScores(state): GameState                // финальные бонусы + winnerIds
autoMove(state): Move                           // ход по умолчанию для таймаута (детерминированный)
toPlayerView(state, playerId): PlayerView       // редактированный вид для рассылки (скрывает состав bag)
```

**`autoMove` — детерминированная спецификация (контракт теста A10):**
из всех легальных ходов выбираем минимизирующий штраф floor; тай-брейк строго по порядку:
(1) меньший индекс источника (фабрики 0..n, центр последним),
(2) порядок цвета в `Color`-перечислении,
(3) меньший номер целевого узорного ряда (floor — последним).
Гарантия: `autoMove` всегда возвращает легальный ход и одинаков для одинакового состояния.

Свойства, которые гарантирует engine (инварианты — проверяются в тестах):
- Сумма всех плиток (фабрики+центр+мешок+сброс+планшеты) всегда = 100.
- `applyMove` к нелегальному ходу не меняет состояние (бросает ошибку).
- Счёт никогда < 0.

## 6. Backend — комнаты, сессии, таймеры, реконнект

**Слои:**
- `engine` (правила) ← `RoomManager` (оркестрация одной игры/комнаты) ← `WsGateway` (транспорт) + `RoomRepository` (хранилище).

**Сессии (гостевой вход):**
- `POST /api/session` `{name}` → `{playerId, token}`. Токен (подписанный JWT или непрозрачный UUID в memory-map) хранится клиентом в `localStorage`.
- WS-подключение авторизуется токеном (query param/первое сообщение `hello`). По токену сервер знает, какой это игрок и в какой комнате он состоит → **реконнект**.

**Лобби / активные комнаты:**
- Комната: `{id, name, hostId, maxPlayers(2..4), players[], status: 'waiting'|'playing'|'finished', isPrivate, createdAt}`.
- REST: `GET /api/rooms` (список waiting-комнат), `POST /api/rooms` (создать), `POST /api/rooms/:id/join`, `POST /api/rooms/:id/leave`, `POST /api/rooms/:id/start` (только host, ≥2 игрока).
- Live-обновление списка лобби — через WS-канал `lobby` (broadcast при изменениях).

**Таймеры ходов + авто-ход (с защитой от гонок):**
- На старте хода сервер ставит таймер (конфиг, дефолт **60с**) и шлёт всем `game:turn{currentPlayerId, deadline}`.
- **Атомарная отмена:** при применении ЛЮБОГО хода (реального или авто) текущий таймер немедленно отменяется. При срабатывании таймера сервер сначала проверяет, что `turnSeq` не изменился (всё ещё тот же ход) — только тогда вызывает `engine.autoMove(state)`. Это исключает двойное продвижение (авто-ход + реальный ход одновременно). Node однопоточен → проверка `turnSeq` + apply атомарны в рамках event loop.
- По таймауту: сервер вызывает `engine.autoMove(state)`, применяет, передаёт ход дальше. Защита от зависания партии при AFK/оффлайне.
- **Инъектируемые часы:** `RoomManager` принимает `clock` (порт `setTimeout`/`now`), как engine принимает RNG-seed. Тесты используют поддельные часы → детерминированно и быстро, без реального ожидания.
- Источник истины таймера — серверный `deadline`-timestamp; клиент только рисует обратный отсчёт.
- **Рестарт сервера:** все активные партии в памяти теряются (принято для MVP). При попытке реконнекта сервер шлёт `game:aborted`/`session:invalid` (см. §7), клиент возвращается в лобби. Никаких «зависших» токенов.

**Реконнект:**
- При обрыве WS игрок помечается `connected:false`, но остаётся в игре; его ходы при таймауте делает авто-ход.
- При повторном `hello` с тем же токеном — сервер шлёт полный `gameState` (его приватный вид) и `connected:true`.

**Хранилище (интерфейс):**
```ts
interface RoomRepository {
  create(room): Room; get(id): Room|null; list(): Room[];
  update(id, patch): Room; delete(id): void;
}
```
Реализации: `InMemoryRoomRepository` (старт) → позже `RedisRoomRepository` без изменений в RoomManager.

## 7. WebSocket протокол (события)

Все сообщения — JSON `{type, ...payload}`, валидируются zod-схемами из `shared`.

**Клиент → Сервер:**
| type | payload | смысл |
|---|---|---|
| `hello` | `{token, roomId?}` | авторизация/реконнект |
| `lobby:subscribe` | — | подписка на список комнат |
| `room:create` | `{name, maxPlayers, isPrivate}` | создать комнату |
| `room:join` | `{roomId}` | войти |
| `room:leave` | `{roomId}` | выйти |
| `room:start` | `{roomId}` | host запускает игру |
| `game:move` | `{move: Move, expectedTurnSeq}` | сделать ход; сервер отклоняет, если `expectedTurnSeq` ≠ текущему (идемпотентность, защита от двойного тапа/устаревшего хода) |
| `ping` | — | keepalive |

**Сервер → Клиент:**
| type | payload | смысл |
|---|---|---|
| `hello:ok` | `{playerId}` | приветствие принято |
| `lobby:state` | `{rooms[]}` | снимок/обновление лобби |
| `room:state` | `{room}` | состав комнаты, статус |
| `game:state` | `{view}` | приватный вид состояния игрока (его рука/планшет + публичные данные) |
| `game:turn` | `{currentPlayerId, deadline}` | чей ход + дедлайн таймера |
| `game:applied` | `{move, by, turnSeq}` | ход применён (для анимаций) |
| `game:over` | `{scores[], winnerIds}` | итоги |
| `game:aborted` | `{reason}` | партия прервана (рестарт сервера, комната уничтожена) → клиент в лобби |
| `player:connection` | `{playerId, connected}` | соперник отключился/вернулся (для индикатора в UI) |
| `session:invalid` | — | токен больше не распознан (после рестарта) → клиент переавторизуется |
| `pong` | — | ответ на `ping` (детект half-open сокета) |
| `error` | `{code, message}` | ошибка (нелегальный/устаревший ход и т.п.) |

**Приватный вид (`view` = `PlayerView`)**: строится чистой функцией `engine.toPlayerView(state, playerId)`. Раскрываем всё публичное (фабрики, центр, планшеты всех, сброс, счёт), но **состав мешка скрываем** — отдаём только `bagCount`. Иначе клиент мог бы вычислять точные вероятности прихода плиток (читерское преимущество). Поле `you` помечает планшет получателя; `turnSeq` нужен клиенту для отправки `expectedTurnSeq`.

## 8. Frontend — экраны, состояние, стиль

**Экраны (роутинг):**
1. **Вход** — ввод ника → `POST /api/session` → сохранить токен. (Авто-вход, если токен есть.)
2. **Лобби** — список активных комнат (live), кнопка «Создать комнату», вход в комнату.
3. **Комната ожидания** — список игроков, индикатор готовности, host видит «Запустить игру».
4. **Игра** — основной экран: рынок (фабрики+центр), планшеты игроков (свой крупно), узорные ряды, стена, пол, счёт, таймер, лог ходов.
5. **Результаты** — финальные очки, бонусы, победитель, «В лобби» / «Реванш».

**Состояние (Zustand):** `session`, `lobby`, `room`, `game`, `connection`. Тонкий слой WS-клиента диспатчит входящие события в стор; UI реактивен.

**Адаптив под телефон:**
- Вертикальная раскладка: сверху твой планшет, ниже — рынок, переключение на планшеты соперников по табам/свайпу.
- Тач-таргеты ≥44px. Выбор хода в 2 тапа: тап по цвету на рынке → подсвечиваются допустимые ряды → тап по ряду (или по полу).

**Визуальный стиль — Azulejo (португальская изразцовая плитка):**
- Палитра: глубокий кобальт `#1B3A6B`, фарфорово-белый `#F4F1EA`, золото `#C9A24B`, терракота-акцент `#9C4A2F`, изумруд `#2E6B5E`.
- Плитки = квадратные изразцы с тонким SVG-орнаментом (бело-синий узор) на цвет; лёгкая керамическая тень/блик, фаска.
- Фон — паттерн азулежу пониженной контрастности (CSS/SVG tile background).
- Типографика: заголовки — высокий контрастный serif (напр. «Cormorant»/«Playfair»), интерфейс — гуманистический sans.
- Микроанимации (Framer Motion): «лёт» плитки от фабрики к ряду, мягкое «защёлкивание» в стену с золотым проблеском при начислении очков, пульс таймера на последних 10с.
- Декоративные рамки-бордюры в духе плиточных панно, золотые разделители.
- Один общий компонент `<Tile color/>` (SVG-орнамент по цвету) — переиспользуется везде.

## 9. План TDD (порядок написания тестов → кода)

**Этап A — Engine (ядро, чистый TDD):**
1. `createGame`: число фабрик по игрокам, 4 плитки/фабрику, инвариант 100 плиток, жетон «1» в центре, пустые планшеты.
2. `isLegalMove`/`legalMoves`: правила источника/цвета/ряда (пустой/тот же цвет/не выложен в стене), переполнение → floor.
3. `applyMove` из фабрики: остальные плитки → центр, фабрика пустеет; в pattern line/на floor.
4. `applyMove` из центра: жетон «1» первому берущему, далее без жетона.
5. `isOfferPhaseOver`.
6. `resolveTiling`: укладка полных рядов; подсчёт смежности (гориз/верт/обе/одиночная); штрафы пола; счёт не <0; жетон возвращается → firstPlayerIndex.
7. `startNextRound`: рефилл, пересыпка сброса в мешок при нехватке.
8. `isGameOver`: завершённая горизонтальная строка.
9. `finalizeScores`: бонусы +2/+7/+10, winnerIds, тай-брейк (общая победа при равенстве).
10. `autoMove`: всегда легален, детерминирован по зафиксированному тай-брейку.
11. `toPlayerView`: состав мешка скрыт (только `bagCount`), всё остальное публично, `you`/`turnSeq` проставлены.
12. Инварианты-проперти: сохранение 100 плиток после любой последовательности легальных ходов; счёт всегда ≥0.

**Этап B — Server (интеграционные тесты с поднятым ws + поддельные часы):**
13. Сессия: создание токена, авторизация WS, отказ при невалидном токене.
14. Лобби: создать/листить/джойнить/лив; broadcast `lobby:state`.
15. Старт игры: только host, ≥2 игрока, статус→playing, рассылка `game:state`/`game:turn`.
16. Ход через WS: легальный применяется и рассылается; нелегальный → `error`, состояние не меняется.
17. **Идемпотентность/гонка ходов:** повторный `game:move` с устаревшим `expectedTurnSeq` отклоняется; двойной тап не продвигает игру дважды.
18. **Таймер vs ход:** при таймауте сервер делает авто-ход (поддельные часы); реальный ход, пришедший после применения, отклоняется по `turnSeq`; нет двойного продвижения.
19. **Реконнект mid-turn:** обрыв → `player:connection{connected:false}` соперникам → повторный `hello` с тем же токеном → актуальный `game:state` + `connected:true`.
20. **Реконнект после рестарта:** токен неизвестен → `session:invalid`/`game:aborted`, клиент в лобби (без зависших токенов).
21. Полная партия E2E на engine+server: от старта до `game:over` с корректным победителем.

**Этап C — Frontend:**
22. Юнит-тесты стора (редьюсеры событий WS, включая `player:connection`/`game:aborted`/`session:invalid`).
23. Компонентные тесты ключевых экранов (лобби, выбор хода в 2 тапа) — Vitest + Testing Library.
24. Ручная визуальная проверка стиля Azulejo на мобильном вьюпорте (скриншоты).

## 11. ADR (ключевые решения)

**Решение:** Монорепо TypeScript с выделенным чистым `engine`-пакетом; сервер-авторитет; WebSocket; in-memory за интерфейсом репозитория.

**Драйверы:** простота и аккуратность (требование пользователя), TDD-дружелюбность, единый источник типов протокола, лёгкий старт с заделом на масштаб.

**Альтернативы:**
- *Логика на клиенте + relay-сервер* — отклонено: читерство, рассинхрон, нельзя авторитетно считать очки/таймеры.
- *socket.io* — отклонено: лишний вес, фолбэки не нужны при PWA + современных браузерах; нативный `ws` проще.
- *Сразу Postgres* — отклонено для старта: замедляет TDD ядра; репозиторий-интерфейс даёт миграцию позже без боли.
- *Монолит без разделения engine* — отклонено: смешение I/O и правил ломает быстрый чистый TDD.

**Последствия:** перезапуск сервера теряет активные партии — это **явно обработано**: при реконнекте клиент получает `game:aborted`/`session:invalid` и возвращается в лобби (никаких зависших токенов). Redis-персист добавляется позже через `RoomRepository` без изменения логики. Один процесс на старте (без горизонтального масштаба и без персиста таймеров — сознательный YAGNI) достаточно для MVP; шардинг по комнатам и персист — позже.

**Follow-ups:** аккаунты/рейтинг, варианты правил (мозаичная стена), Redis-персист, наблюдатели (spectators), реванш-серии, звук.
